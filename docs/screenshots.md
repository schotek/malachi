# Screenshots of the three clients

The website (`web/`) and the README show the app over one sample world on
every platform: the same people, the same mail, the same Jira issues and
the same CRM records, photographed in the same scenes in English and in
Czech. This document is the hand-over for whoever takes the Linux and
Windows sets: what the world is, how it is started, which scenes to take,
how the macOS set was made, and how the images come back.

Status (2026-10-28): the macOS set (11 scenes × 2 languages) is done and
approved by the owner; it was made with `scripts/screenshots/macos.sh`.
The Linux (GTK) and Windows sets are pending, one agent each (§5, §6).
The images are not in the repository: the macOS ones are regenerated by
the script, the others come back on a throwaway branch (§7).

## 1. The sample world

`backend/cmd/malachi-devmail` is a developer tool, built by hand (`go
build ./cmd/malachi-devmail` in `backend/`; the Makefile and the packages
never ship it). `malachi-devmail serve` is three servers in memory on
127.0.0.1: a plaintext IMAP server with IDLE and a plaintext SMTP
submission server (the mail), a fake Jira Cloud site
(`internal/jira/jiratest`) and a fake eWay-CRM instance
(`internal/eway/ewaytest`), seeded with the sample set of one language
(`samples/en.json`, `samples/cs.json`: one story in two languages, dates
relative to the clock the server starts with). `malachi-devmail
add-account` performs the daemon's handshake and adds the three accounts
the way a client would, and saves the set's saved conversation into the
CRM. The binary is also the daemon's keyring helper (`get`, `set`,
`delete`), writing the secrets to a JSON file, so the daemon runs with
no system keyring at all. Every password is `test`.

The world:

- **Jana Dvořáková** (`jana.dvorakova@example.test`, Kovar Engineering),
  the user. Colleagues Tomáš Holub, Lucie Marková and Martin Beneš;
  customers Petr Svoboda (Acme Logistics) and Eva Králová (Bluebird
  Studio); Ondřej Vlk (Copywrite); a mailing list and a newsletter.
- **Mail**: 26 messages — 17 in the Inbox, 5 in Sent, one each in Drafts,
  Trash, Junk and Archive — among them the quotation conversation with
  Acme (four messages, two of them her replies), a meeting invitation
  with a calendar part, a newsletter with one-click unsubscribe, a
  mailing-list thread, an order confirmation, a phishing mail in Junk
  and a conference programme with attachments.
- **Jira** (account *Acme Jira*): spaces ITSD, WEB and MOB with seven
  issues, comments, status changes and one issue assigned to Jana; the
  web issue WEB-1 is the one photographed.
- **eWay-CRM** (account *eWay-CRM*): the companies Acme Logistics,
  Bluebird Studio and Copywrite, their contacts, two deals, two projects,
  and the quotation reply saved to the CRM with links to Petr Svoboda,
  Acme Logistics and the deal *Acme: warehouse extension, hall B*.
- **The Board** evaluates the mail to 17 cases in either language.
- **The Calendar** has no server in the world: the scenes use the
  clients' built-in samples (`MALACHI_CALENDAR_SAMPLES=1`), which every
  client has. The invitation card in Mail comes from the mailbox.

### Starting it

`scripts/screenshots/stack.sh start en` (or `cs`) builds `malachid`,
`malachi-devmail` and `malachi-rpc` from the tree into `DIR/bin`
(`DIR` = `/tmp/malachi-shots`, or the third argument), wipes `DIR/data`,
starts the servers on the ports 11143 (IMAP), 11025 (SMTP), 11080
(control), 11090 (Jira) and 11095 (eWay-CRM), starts the daemon over
`DIR/data` with the socket `DIR/rpc.sock`, the helper keyring and
`MALACHI_TIME_ZONE=Europe/Prague`, adds the accounts and waits until the
Board reports its 17 cases. `stack.sh stop` ends it. It runs on macOS
and on Linux (in the Fedora container too); on Windows the same steps are
run by hand (§6). The client is then started with `MALACHI_DAEMON=none`,
`MALACHI_SOCKET=DIR/rpc.sock` and a data directory of its own, never
over the real store or the real preferences.

Each language is a fresh world: `stack.sh start cs` after the English
set, and the client in Czech (how, per platform below).

The rules every scene follows:

- **The window**: 1440×900 logical pixels, the sidebar shown, the
  assistant panel closed, the list filter on *All*, the reading pane with
  the message. Nothing else on the picture: the client's window with its
  title bar (or the compose window alone), no shadow, no desktop, no
  other window, no mouse pointer, no notification, no toast.
- **Scale**: 2 device pixels per logical pixel, so 2880×1800 px for the
  main window; the macOS set was taken on a Retina display. What the
  other platforms can do is in §5 and §6; an image is never resampled
  afterwards.
- **Look**: the light appearance, the system's default accent colour,
  the default fonts, zoom and density. Nothing in the picture may be a
  real account, a real name or a real address: only the world above.
- **Language**: `en` is English with the region *United Kingdom* (dates
  as 28/10/2026), `cs` is Czech with *Czechia*. The sample set in the
  matching language, started afresh for each.
- **Time**: the sets are relative to the real clock, so nothing is set;
  every platform shows the dates of the day it was photographed.
- **Before the first scene** the daemon has finished its first
  synchronisation (`stack.sh` waits for that), so every folder has its
  messages and counts and no "connecting" or sync banner shows.

## 3. How the macOS set was made

`scripts/screenshots/macos.sh en OUTDIR` over a running `stack.sh start
en`: it assembles a throwaway bundle (bundle id
`io.github.schotek.Malachi.shots`, its own preferences domain, the debug
build of the Swift package with the SDK recorded by `vtool` as
`macos/Makefile` does, the icon and the `.lproj` directories through the
Makefile's recipes, ad hoc signed), writes the language and region into
that domain, and runs the app twice with `MALACHI_START`
(`MainWindowController+DevStart.swift`), which puts the window through
the scenes and writes each PNG itself. The steps the scenes use, which
the Linux port mirrors (§5):

| Step | What it does |
|---|---|
| `group=on` / `group=off` | the *Group by Conversation* setting |
| `chat=on` / `chat=off` | the *Show as Chat* setting (`conversation-chat-layout`) |
| `folder=<text>` | shows the first folder of any account whose **server** name contains the text (`inbox`, `sent`, `Web`), as a click in the sidebar |
| `row=<text>` | selects the first row of the list whose subject contains the text, case-insensitively, as a click |
| `mail`, `board:list`, `board:columns`, `calendar:week` | the mode, style and view; `board:list:select` also selects the case with the most conversation text |
| `compose-open` | *New Message* (a blank window) |
| `crm-save` | *Save to eWay-CRM…* over the selected message (the dialog stays open) |
| `shot=<path>` | the key window as a PNG (the window the sheet belongs to, with the sheet drawn over it) |
| `size=WxH`, `quit` | the window's size; the end (an open sheet is dismissed first) |

The two runs, with `MALACHI_START_INTERVAL=4` seconds per step and
`MALACHI_START_SIZE=1440x900`:

```
group=on;chat=off;row=DevConf;shot=inbox.png;row=Quotation;chat=on;shot=chat.png;
chat=off;row=Q4 planning;shot=invitation.png;row=Design Weekly;shot=newsletter.png;
folder=Web;row=WEB-1;shot=jira.png;board:list:select;shot=board-list.png;
board:columns;shot=board-columns.png;calendar:week;shot=calendar-week.png;
mail;folder=inbox;row=DevConf;compose-open;shot=compose.png;quit

group=off;chat=off;folder=sent;row=Quotation;shot=crm-saved.png;
folder=inbox;row=Request for a quote;crm-save;shot=crm-dialog.png;quit
```

(In Czech: `Nabídka`, `Porada`, `Poptávka` for the three subjects.) The
app brings itself to the front before each shot; whatever is over it
meanwhile would be in the picture, so the Mac is left alone for the two
minutes a run takes.

## 4. What is the same on every platform

The world, the scenes, the window size and the rules of §2. The
platform's own look is wanted, not an imitation of another: the native
title bar, dialogs where the platform puts them (a sheet on macOS, a
dialog inside the window on GTK and Windows), the compose window at the
platform's default size, the toolbar as the client lays it out. The
sample data must not be changed for a platform: if a scene cannot be
reproduced, it goes into the notes of the hand-over, not into the JSON.

## 5. Linux (the GTK client)

Environment. The client is built and run as in `CLAUDE.md`
(*Prostředí*): on a Mac in the Fedora 42 container
(`scripts/gtk-container/gtk.sh make build` → `build/linux/malachi`,
`gtk.sh shell` for a shell inside, where Go and the X tools are), or on
a Linux desktop with the same packages (`scripts/gtk-container/rpm.yml`).
Inside the container `stack.sh start en` builds and starts the world as
on macOS (the `/src` tree is the repository). The display:

- **Xvfb** is the deterministic choice (`gtk.sh test-ui` runs the UI
  tests under it): `Xvfb :99 -screen 0 2880x1800x24`, the client with
  `DISPLAY=:99 GDK_BACKEND=x11 GDK_SCALE=2` so that 1440×900 logical
  pixels are 2880×1800 device pixels and the window fills the screen.
  No window manager: the window sits at 0,0 and GTK draws its solid
  client-side frame without a shadow (no compositor), which is exactly
  the picture wanted. A desktop session (XQuartz through `gtk.sh x11`, a
  GNOME session) works too when its screen is 2× and the window can be
  1440×900 logical; then the shot is cropped to the window.
- **The look of a GNOME desktop** comes from `gtk-4.0/settings.ini`
  (the Adwaita Sans 11 UI font, the Adwaita icon and cursor themes,
  GNOME's font rendering): take the block `gtk.sh x11` writes
  (`gtkini=` in `scripts/gtk-container/gtk.sh`). Light: no
  `gtk-application-prefer-dark-theme`, the default colour scheme.
  `librsvg2` must be in the image (it is since 2026-10-20; without it
  every SVG icon is `image-missing`).
- **The environment of the client**, as `gtk.sh x11` sets it:
  `GSETTINGS_SCHEMA_DIR=/src/build/linux/glib-2.0/schemas`,
  `GSETTINGS_BACKEND=keyfile` with a keyfile under
  `$XDG_CONFIG_HOME/glib-2.0/settings/keyfile` that sets
  `window-width=1440` and `window-height=900` (and may preset
  `group-by-conversation` and `conversation-chat-layout` per scene
  instead of a step), `MALACHI_LOCALE_DIR=/src/build/linux/locale`,
  `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1` (only in the Apple
  container, where bwrap cannot make its namespaces),
  `MALACHI_DAEMON=none`, `MALACHI_SOCKET=/tmp/malachi-shots/rpc.sock`,
  `MALACHI_CALENDAR_SAMPLES=1`, `XDG_RUNTIME_DIR`, `XDG_CONFIG_HOME`,
  `XDG_DATA_HOME` and `XDG_CACHE_HOME` under a throwaway directory
  (never the user's own: dconf and the preferences would follow).
- **Language**: `LANG=en_GB.UTF-8` for the English set, `LANG=cs_CZ.UTF-8`
  for the Czech (both locales are in the image: `glibc-langpack-en`,
  `glibc-langpack-cs`); `TZ=Europe/Prague`.

Driving. `MALACHI_GTK_START` (`ui/internal/window/devstart.go`) is the
GTK counterpart of `MALACHI_START`; today it has `mail`, `board`,
`calendar:week`, `size=WxH`, `quit` and the dialogs, not the scene
steps. Port the missing ones from §3 with the same names and meaning:
`row=` (the first row of the list whose subject contains the text;
select as a click would), `folder=` (the first folder whose server name
contains the text; `Window.selectFolder` as the sidebar does), `chat=`
and `group=` (the two settings keys), `board:list`, `board:columns`,
`board:list:select` (the case with the most conversation text),
`compose-open` (`app.compose`), `crm-save` (`win.crm-save`), and a way
to take the picture: either `shot=<path>` inside the app (a render of the
window through `gsk_renderer_render_texture` and `gdk_texture_save_to_png`
is worth a try, but the WebKit views may come out empty, in which case
it is not the way) or a line `MALACHI_GTK_START shot <path>` on stderr
that a driver script answers from outside with the X server's image
(`import -window root` from ImageMagick, or `xwd -root` and `convert`),
cropped to the window's geometry (`xwininfo -root -tree`, `xdotool`).
`parseDevStart` has tests in `devstart_test.go`; the new steps get
theirs. The dev-start code is a development aid like the macOS one, not
a feature: nothing of it runs without the variable, and nothing of it
is translated.

Scene notes. `crm-dialog.png`: the *Save to eWay-CRM* dialog is an
`Adw.Dialog` inside the window, so the window's picture has it;
`compose.png`: the compose window is a toplevel of its own; crop to it
(its own default size). The `shot` must come after the step has laid
out: WebKit needs a moment to render a body, so the interval between
steps stays at a few seconds and the picture is taken when the body is
drawn (the macOS run uses 4 s). Check the pictures for `image-missing`
icons, tofu glyphs and an empty reading pane before handing them over.

## 6. Windows (the WinUI 3 client)

Environment. Windows 11, the toolchain of `CLAUDE.md` (*Prostředí*):
`windows\build.ps1 app` publishes `build\windows\x64\Malachi Mail\`
with `MalachiMail.exe`, `malachid.exe` and the helpers. The world is
started by hand, with the same steps as `stack.sh` (PowerShell):

```powershell
$dir = "$env:TEMP\malachi-shots"          # short: the socket path is limited to 107 bytes
New-Item -Force -ItemType Directory "$dir\bin", "$dir\data" | Out-Null
Push-Location backend
go build -o "$dir\bin\malachid.exe" .\cmd\malachid
go build -o "$dir\bin\malachi-devmail.exe" .\cmd\malachi-devmail
go build -o "$dir\bin\malachi-rpc.exe" .\cmd\malachi-rpc
Pop-Location
$env:MALACHI_DEVMAIL_KEYRING = "$dir\data\keyring.json"
Start-Process "$dir\bin\malachi-devmail.exe" -ArgumentList "serve -lang en -imap-port 11143 -smtp-port 11025 -control-port 11080 -jira-port 11090 -eway-port 11095"
$env:MALACHI_KEYRING = "helper"; $env:MALACHI_KEYRING_HELPER = "$dir\bin\malachi-devmail.exe"
$env:MALACHI_TIME_ZONE = "Europe/Prague"; $env:MALACHI_LOG_LEVEL = "info"
Start-Process "$dir\bin\malachid.exe" -ArgumentList "--config $dir\data\config.toml --store $dir\data\store.db --socket $dir\rpc.sock"
# wait for $dir\rpc.sock and $dir\rpc.sock.key, then:
& "$dir\bin\malachi-devmail.exe" add-account -socket "$dir\rpc.sock" -imap-port 11143 -smtp-port 11025 -jira-port 11090 -eway-port 11095 -lang en
# until (& "$dir\bin\malachi-rpc.exe" --socket "$dir\rpc.sock" board.list '{}') lists 17 cases
```

The daemon's socket directory must be under the user's profile
(`%TEMP%` is): a directory others may write to ends in *Backend
unavailable*. The app runs with `MALACHI_DAEMON=none`,
`MALACHI_SOCKET=$dir\rpc.sock`, `MALACHI_DATA_DIR=$dir\appdata`,
`MALACHI_SETTINGS_KEY=io.github.schotek.Malachi.shots` (a preferences
key of its own under `HKCU\Software`, deleted afterwards) and
`MALACHI_CALENDAR_SAMPLES=1`, as the UI smoke tests' `AppSession` runs
it; nothing of this touches the user's own data, preferences or
registrations. (The note in `CLAUDE.md` on the Claude Desktop MSIX
container applies to anything that must reach the real registry;
nothing here must.)

Language. The client follows the Windows display languages
(`GetUserPreferredUILanguages`; `docs/windows-port.md` §9) and reads the
catalogue from `locale\` beside the exe, so the Czech set needs Czech
first in *Settings → Time & language → Language & region* (a sign-out
applies it), or a development override of the preferred languages
(an environment variable read before `WindowsPreferredLanguages`, a
Windows-only aid documented like `MALACHI_SETTINGS_KEY`). Either is
fine; the notes say which. The region: English (United Kingdom) for `en`,
Czech for `cs`.

Driving. The client has no `MALACHI_START`. Two ways, both acceptable:
a port of it into `Malachi.App` (the same step names as §3, a
development aid that runs only with the variable; `MainWindow` gets the
list and mailbox hooks the steps need, as the macOS window got
`developmentList` and `developmentMailbox`), or UI Automation from a
small driver reusing `Malachi.App.UiTests` (`AppSession`, `Uia`: the
`MessageList` items by name, the sidebar's folders, the mode switch,
the toolbar's buttons), with the two settings (`group-by-conversation`,
`conversation-chat-layout`) written into the preferences key before the
start instead of clicked. The capture: the window brought to the front
and fully on screen, its rectangle from `DwmGetWindowAttribute` with
`DWMWA_EXTENDED_FRAME_BOUNDS` (the frame without the invisible resize
borders), the pixels with `Graphics.CopyFromScreen`
(`System.Drawing`); `PrintWindow` with `PW_RENDERFULLCONTENT` is the
alternative that includes WebView2's content without the window being
in front. A `ContentDialog` (*Save to eWay-CRM*) is inside the window;
the compose window is a window of its own (*New Message* / *Nová
zpráva*): captured alone.

Scale. The set wants 2 device pixels per logical pixel: a display at
200 % with room for a 1440×900 logical window plus the taskbar (a 4K
display), or *Settings → System → Display → Scale* set to 200 % for the
run (new processes take the new scale). Where that is not possible, the
display's native scale (150 % gives 2160×1350 px, 100 % gives 1440×900 px)
with the window still 1440×900 logical, and the scale in the notes. The
light theme, the default accent colour, Mica as the app has it.

As built (2026-10-28, branch `shots/windows`): the port of
`MALACHI_START` into `Malachi.App` (`MainWindow.DevStart.cs`, the parser
in Core's `DevelopmentStart` with tests; `docs/windows-port.md` §12), the
language override `MALACHI_LANGUAGES` (`docs/windows-port.md` §9: the
tags, and the first one as the regional format) and
`scripts/screenshots/windows.ps1`, which starts the world as the block
above does (`start en|cs`) and runs the app through the two scripts of
§3 (`shots en|cs OUTDIR`, with `MALACHI_START_SIZE=1440x900` — the
visible frame, so the picture is 2880×1800 px at 200 % — and
`MALACHI_START_INTERVAL=4`); the first run begins with `folder=inbox`,
as the Linux set does. The window stands in the top left corner of the
work area, not in its centre: an unactivated Windows draws its
watermark above the bottom right of the screen, over a window there;
the compose window is moved to the same corner for its picture, since
the translucent border line under a window's top edge would otherwise
show the main window's text. The `shot=` step writes the PNG itself
once the reading pane's web view has loaded and the eWay-CRM dialog's
lookup has answered: the window brought to the front, its extended
frame bounds intersected with its client area copied from the screen
(Mica, the WebView2s and a `ContentDialog` as the user sees them), or
rendered by `PrintWindow` when it could not take the foreground, which
the step's line on stderr says.

## 7. The hand-over

One branch per platform from `main` (at or after the commit that added
this document, which carries `malachi-devmail` and the daemon changes
it needs): `shots/linux`, `shots/windows`. On it, first the code
commits as usual (the dev-start steps with their tests, a language
override, a fix found on the way; conventional commits, the SPDX
headers, nothing in `web/`, `README.md` or `docs/screenshots/*.png`),
then as the **last** commit the pictures:

```
docs/screenshots/handover/<platform>/en/<scene>.png      11 files
docs/screenshots/handover/<platform>/cs/<scene>.png      11 files
docs/screenshots/handover/<platform>/NOTES.md
```

PNG, lossless, unscaled, named exactly as in §2. `NOTES.md` says: the
OS and its version, the display scale and the pixel size of the main
window's picture, how the client was driven (the steps or the driver)
and the exact environment, the language setup, which scenes differ from
§2 and why, and anything that could not be reproduced. Push the branch
and tell the owner. The branch is never merged as it is: the Mac
session takes the pictures, converts them for the website and the
README, cherry-picks the code commits onto `main` and deletes the
branch, so that the PNGs do not stay in `main`'s history.

Before pushing, a look at every picture against §2: 22 files, the window
1440×900 logical, light, all text rendered (no missing glyphs, no
`image-missing` icons), the reading pane with the body, no pointer,
toast, notification or other window, the sidebar with the three
accounts, no "backend unavailable" or sync banner, the folder counts of
the set (17 in the Inbox).

## 8. After the hand-over

On the Mac, `web/README.md` says how the pictures become the site's
`assets/screenshots/*.webp` (1600 px wide, `cwebp -q 82 -sharp_yuv`)
and the README's table; the gallery takes one set per platform in each
language.
